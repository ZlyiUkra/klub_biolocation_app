# Parity inventory: what the old application does, and where the rewrite carries it

Written 2026-10-10. Purpose: nothing the old application does is lost in the rewrite without a decision. The old
application is the live site, `klub_biolocation_astro` (commit `2b4aac9` and the later work of its branches); the
new plan is `specs/001-self-hosted-club-site/` (`spec.md`, `plan.md`, `data-model.md`, `research.md`, `tasks.md`,
`contracts/http-api.md`). This file was produced by reading both and checking each claim against the task text; where
the text could not be verified it says so.

## How to read the tables

- **Where in old app**: the file or the document section that holds the behaviour.
- **New task id(s)**: ids from `tasks.md`. "frontend kept" means the Astro component or script is carried unchanged
  into the new repository (the plan keeps `src/` as it is) and is covered by the parity tasks T133 and T134, not by a
  task of its own. "none" means no task names it.
- **Status**: `covered`, `partly covered (Gn)`, `NOT COVERED (Gn)`, or `dropped by decision (source)`. Every row that
  is partly covered or not covered has a gap id `Gn`, and section "Gaps" gives the recommendation.
- Test counts of the old Workers, as `tasks.md` states them: 129 content cases, 68 status cases, 56 video-access cases.
